## 명세와 다르게 하거나 덧붙인 점 (계약 5장은 바꾸지 않음)

함수 이름·반환형(`extract(doc) -> dict[str, FieldValue]`, 다섯 칸 모두, method='rule')은 계약 그대로다. 부록 C의 세부 규칙에서 다음을 판단해 바꾸거나 더했다. 빼려면 각각 한두 줄만 고치면 된다.

1. **라벨 추가(C.4)**: content에 추진목적·추진배경·행사개요, qualify에 응모대상·입주대상, area에 응모유형을 더했다(`rules.SUPPORT`). 실제 공고문의 같은 뜻 라벨이다. '참가대상'·'참여대상'은 행사 청중 문장에 걸려서 넣지 않았다.
2. **입찰공고 라벨 보충**: 입찰 라벨(C.4 입찰 열)로 못 찾으면 공모지원사업 라벨로 한 번 더 찾는다. v2에서 입찰공고로 분류되는 위탁연구·[공모] 공고서가 '신청자격'·'사업목적' 라벨을 쓰기 때문이다.
3. **개요 파서 일반화(C.6 NIA)**: '일반사항'·'입찰에 부치는 사항'(+ '대상과제'·'입찰개요') 개요 파서를 NIA뿐 아니라 모든 기관의 입찰공고에 쓴다. 입찰공고에서는 제안요청서·규격서의 '사업 개요'·'구매 개요'·'과업 개요' 머리도 개요로 본다. content는 '건명: … / 기간: … / 예산: …' 줄이다(KCA C.6과 같은 꼴). 머리 행 + 값 행으로 된 표도 읽는다. NIA 게시판에서는 유형과 상관없이 라벨로 못 찾을 때의 content 보충으로 쓴다.
4. **입찰 분야 대체값**: 계약방법 라벨 순서는 계약입찰방법 > 입찰방법 > 입찰방식 > 계약방법 > 추진방법 > 선정방법이다(뒤의 둘은 [공모]형 공고서용). 말머리(biz)가 유형 표시일 뿐이면(입찰공고·조달입찰공고·사전규격공개·공모·위탁연구·모집공고 등) '분류:' 줄을 넣지 않는다. 값은 '분류: <biz>\n계약방법: <값>'이고 note는 '대체값'이다. 계약방법이 없고 biz만 있으면 source=site다.
5. **머리 기호(C.3)**: ◐ ▪ o ➊ ❶을 더했고, 점 없는 로마 숫자('Ⅰ 사업 개요')와 RAPA의 번호 표 머리('| 2 | | 공고 개요 |' → '1.' 수준)도 머리로 본다. 수준은 고정 순서(# · Ⅰ > 1. > □ > 가. > ○ > 1)·①)다.
6. **오탐 거르기 보강**: (a) 라벨 앞에 쉼표나 닫히지 않은 괄호가 있으면 문장 속 라벨로 보고 버린다. (b) 값 구분(':'·'(라벨)') 없이 40자를 넘는 머리 줄은 문장으로 본다. (c) 목차: 점선·쪽 번호 끝 외에, 머리 줄과 구획 줄의 60% 이상이 쪽 번호로 끝나면 목차 덩어리로 본다. (d) '라벨 \| 값' 표 줄의 값에 전화·이메일이 있으면(문의처 표) 버린다.
7. **첨부 제외**: FORM_WORDS 외에 이름에 규정·지침·규칙·법률·시행령·시행규칙·매뉴얼·조례·고시가 든 첨부(참고 법령·지침 묶음)는 읽지 않는다. 안에 '지원대상' 같은 말이 많다.
8. **연락처 가림**: 규칙이 만든 value·evidence는 `mask.mask_contacts`로 이메일·전화번호를 가린다. 첨부 원문에는 담당자 연락처가 그대로 있고, CLAUDE.md 데이터 규칙상 화면에 그대로 나가면 안 되기 때문이다. 사이트 칸(제목·기간)은 손대지 않았다.
9. **기간(C.5)**:
   - 명세 순서대로 `extract_period`를 먼저 쓴다. 이 함수는 라벨 우선순위가 없어 공고기간과 접수기간을 둘 다 읽을 수 있으면 먼저 나온 것을 낸다. 우선순위는 보강 파서에만 적용된다(시험으로 고정).
   - '24:00'은 '23:59'로 바꾼다.
   - Doc에 posted_at이 없어서, 연도 없는 날짜에는 사이트 기간의 연도, 그것도 없으면 글에 처음 나오는 온전한 날짜의 연도를 쓴다.
   - 충돌은 사이트 칸과 '본문 또는 첨부에서 처음 찾은 값'의 시작일·마감일을 날짜 단위로 비교해 하나라도 다르면 '충돌'이다. note는 '본문: <근거 줄>' 또는 '첨부(<파일명>): <근거 줄>'이다.
10. **KCA**: 입찰개요 표 키에 조달청 물품입찰공고서 형식(공고명·사업금액·납품기한·계약입찰방법)도 넣었다. KCA 본문은 출처에서 아예 뺀다(고정 문구).

## 알게 된 문제·코디네이터 확인 사항

- **충돌 판정 범위**: NIPA 16931은 이 PC의 DB 기준으로 사이트가 2026-09-11 16:52 ~ 09-30 23:00이고, 본문·첨부 모집 기간은 ‘26.09.15 ~ 09.30이다. 시작일이 달라 '충돌'이 된다. 핸드오프의 2025/2026 오기 사례와는 데이터가 다르다. NIPA 사이트 시작이 게시 시각인 경우가 많아, 시작일 차이까지 충돌로 보면 충돌이 늘 수 있다. 마감일만 비교하려면 `rules._period`의 `pairs`에서 시작 쌍을 빼면 된다.
- **관문 2 표본**: 정답표의 공모지원사업은 18건이다(관문 기준은 20건). KCA period 기준(≥ 8/10)은 위 이유로 이 표본으로는 넘을 수 없다. 기준을 '기간이 있는 KCA 입찰공고 중'으로 바꿀지 결정이 필요하다.
- **기타 유형 content**: 라벨 구획이 없으면 '미확인'이다(명세대로, 본문 앞부분으로 채우지 않음). 기타는 API 보완 대상이 아니어서 화면에 '원문 확인 필요'가 자주 나올 것이다(표본: RAPA 7628, NIA 30212).
- **area(공모지원사업)**: 채움 27.8%다. C.4 라벨을 쓰는 공고가 적다. API 보완이 필요한 칸이다.
- **'db' 지표 준비**: `--pred db`는 DB의 `announcement_fields`를 그대로 읽는다. 지금 `attach_text.targets`는 본문이 짧은 공고만 고르므로, NIA처럼 본문이 긴 표본은 `attach-text --any-body`로 첨부를 읽은 뒤 `extract-fields`를 돌려야 규칙만 지표와 같은 입력이 된다.
- **기존 추출기(legacy) 글자**: kordoc이 실패해 `extract.py` 글자가 들어온 첨부는 실제 표본으로 시험하지 않았다. 한 줄이 평균 400자를 넘으면 `split_flat`으로 머리 기호 앞에서 나눈다.
- **zip 글자 형식 의존**: zip 행은 `attach_text.read_zip`이 쓰는 '### <안의 이름>' 머리(확장자로 끝나는 줄)로 나눈다. 이 형식이 바뀌면 `rules._ZIP_PART`도 맞춰야 한다.
- 공개 API·엑셀에는 손대지 않았다(2.3 기본값).
