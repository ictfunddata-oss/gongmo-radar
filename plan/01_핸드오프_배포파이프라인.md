# 핸드오프 — 웹앱 배포용 수집·분류·자동화 파이프라인

- 작성: 2026-11-24 · 상태: **설계와 분류 프롬프트 검증 완료, 구현 전.** 이 작업에서 앱 코드와 DB 스키마는 고치지 않았다.
- **구현은 `00_구현핸드오프.md` 한 문서로 맡긴다**(2026-11-24 2차 Q&A 반영). 이 문서는 그 배경(현황·설계 근거·v1 검증 수치)이다. 분류 v1 런타임 프롬프트는 `prompts/classify_v1.*`, 첨부 읽기 판단은 `03_kordoc_도입검토.md`에 있다.

## 1. 결론 요약

1. **분류 런타임 프롬프트(classify_v1)는 그대로 배포 파이프라인에 써도 될 수준이다.** Sonnet 5.5(`claude-sonnet-5-5`, effort low)로 수집분 1,010건을 기관별 50건 묶음 21회로 돌렸다.
   - 형식 오류·누락·실패: 0건
   - 앞선 Orca 분할 분류와 일치: 98.9%
   - 같은 설정으로 다시 돌린 결과와 일치: 99.8%
   - 어긋난 건은 위탁연구·공모사업의 사전공개 같은 경계 사례에 몰려 있었고, 이 규칙들은 ADR-048에서 v2로 확정했다(v2 작성·재검증 전).
2. **비용은 문제가 되지 않는다.** 1,010건 분류에 캐시가 차 있으면 $0.74, 처음이면 $2.39가 들었다(CLI가 보고한 API 환산 비용). 새 공고는 한 달 80~90건 수준이라 월 $1 미만이다.
3. **배포 형태는 컨테이너(Python + Node 20)와 영구 저장소 조합을 권한다.** 수집·분류·kordoc은 웹 요청과 떨어진 워커 프로세스에서 돈다. 저장소에 있는 `.vercelignore`가 가리키는 Vercel 서버리스는 이 구조와 맞지 않는다(4.5). ADR-046으로 컨테이너 배포를 확정했다.
4. **kordoc은 CLI 하위 프로세스로 넣을 수 있다.** HWP·HWPX 표를 보존하는 데 효과가 크고, 이미지 PDF는 OCR로 일부 살린다. zip은 앱에서 먼저 풀어야 한다(`03`).
5. **배포 전에 고칠 버그가 있다.** 첨부를 받는 동안 DB 쓰기 잠금을 쥐는 문제, 자동화 잠금의 박동 문제 등이다(2.3).

## 2. 현재 상태 (사실)

### 2.1 앱
- Flask 3 + SQLite(WAL). 4개 기관 어댑터(NIPA 사업공고·NIA 입찰공고·KCA 입찰공고·RAPA 공지사항).
- 수집은 `flask --app run crawl`로 돌고, 자동화는 `automation/`(웹 안 스레드 또는 `automation-daemon`, DB 잠금 박동)가 맡는다.
- **AI 분류 코드는 없다.** 2026-11-20에 공고 AI 판별·분류 기능을 모두 삭제했다(ADR-044). 이 계획은 분류를 API로 다시 넣는 것이므로 **새 결정 기록이 필요하다**(6장 1번).

### 2.2 데이터 (2026-11-24 수집, 최근 약 1년치)
- 공고 1,010건(NIPA 60 · NIA 600 · KCA 150 · RAPA 200), 첨부 2,176개, 수집 오류 0
- 유형 분포(Orca 분류): 공모지원사업 216(21%) · 입찰공고 675(67%) · 기타 119(12%). 상세는 `.team/out/summary.md`
- 표준 필드(공고명·내용·자격·분야·기간) 분석: `docs/핸드오프/상세화면_표준필드_20261124.md`

### 2.3 배포 전에 고칠 것 (2026-11-24 코드 분석에서 확인)

| 문제 | 위치 | 영향 | 확인 방법 |
|---|---|---|---|

| `SECRET_KEY` 기본값이 공개된 문자열 | `app/config.py` 25행 | 비밀번호 해시만 환경 변수로 넣고 키를 빠뜨리면 세션 위조 가능 | 코드 확인 |

| 공개 검색어 기록에 제한이 없음 | `app/web/public.py` 57행 | 같은 요청 두 번으로 홈 '많이 찾는 검색어'에 임의 문구가 노출된다 | 재현함 |

## 3. 목표 구성

```
 워커 프로세스 (flask --app run automation-daemon, 예약 실행)
   ├─ ① 수집          crawler.crawl()  ─────────────→ announcements · attachments
   ├─ ② 첨부 글자      zip 풀기 → kordoc CLI(hwp·hwpx 우선, pdf) → 실패 시 extract.py
   │                                    ─────────────→ attachments.text_body / text_status
   ├─ ③ 분류          Claude API  claude-sonnet-5-5 · classify_v1 · 구조화 출력
   │                  (새 공고: 동기 호출 50건 묶음 / 재분류·백필: Message Batches)
   │                                    ─────────────→ announcement_labels (사람 수정값 우선)
   ├─ ④ 표준 필드      다음 단계: 규칙 → 남은 '미확인'만 API (docs/핸드오프 문서)
   └─ 기록            automation_runs + llm_calls(토큰·비용·요청 ID·대체 여부)

 웹 프로세스 (gunicorn, AUTOMATION_SCHEDULER=0)
   └─ 수요자 화면·운영 화면 (읽기 위주. 라벨로 유형 필터, 노출 정책은 6장 4번 결정 뒤)
```

## 4. 단계별 설계

### 4.1 수집
지금 코드를 그대로 쓰되, 2.3의 앞 두 버그는 먼저 고친다. robots.txt 확인과 0.3초 간격은 유지한다(원칙 P6).

### 4.2 첨부 글자
`03_kordoc_도입검토.md`의 A안(CLI 하위 프로세스)을 쓴다. zip을 풀고, hwp/hwpx를 pdf보다 먼저 읽고, 실패하면 기존 추출기로 넘어간다. OCR은 글자가 0인 PDF에만 쓰고 기본은 꺼 둔다.

### 4.3 분류 (API)

| 항목 | 정한 값 | 근거 |
|---|---|---|
| 모델 | `claude-sonnet-5-5` | 사용자 지정. 입력 $2 / 출력 $10 (100만 토큰당) |
| 프롬프트 | `prompts/classify_v1.system.md`(시스템) + 입력 `<items>` JSON | CLI로 검증한 것과 같은 파일 |
| 출력 | `output_config.format` = `classify_v1.schema.json` (json_schema) | 형식 오류 0건(2회 × 1,010건) |
| effort | `low` | 분류 작업. low에서 일치율 98.9%, 재현성 99.8% |
| thinking | 생략(적응형 기본) | Sonnet 5.5는 `disabled`가 400 |
| 묶음 | 50건 | 호출당 11~18초, 출력 약 3천~4천 토큰 |
| 캐시 | 시스템 프롬프트에 `cache_control` | 프롬프트가 캐시 최소 길이(512토큰)를 넘는다. 실행 안 묶음끼리 재사용 |
| 거절 대비 | 동기 호출: `fallbacks="default"` (beta `server-side-fallback-2026-07-01`) | 스킬 권장 기본값. Batches에서는 쓸 수 없다 |
| 대량 처리 | Message Batches API | 50% 할인. 전체 이력 재분류 같은 백필용 |
| 금지 | `temperature`·`top_p`·`top_k`, assistant prefill | 이 모델에서 400 |
| 보내는 값 | 제목·말머리·상태·기간·게시일·본문 앞 300자(연락처 가림)·첨부 이름 | 작성자(담당자 이름)는 보내지 않는다 |
| 저장 | `announcement_labels`(+ prompt_version·model·request_id·input_hash), `llm_calls` | 사람이 고친 값 우선(원칙 P3), 재현성(원칙 P2) |

### 4.4 자동화
기존 파이프라인에 ②·③ 단계를 스위치(기본 꺼짐)로 붙이고, 실행당 분류 상한(기본 200건)을 둔다. 한 단계가 실패해도 다음 단계는 돈다. 박동은 긴 단계 안에서도 갱신한다.

### 4.5 배포 형태
- **권장**: 컨테이너 하나에 Python 3.12와 Node 20(kordoc)을 담는다. 프로세스는 둘로 나눈다(웹 `gunicorn run:app` + 워커 `automation-daemon`). SQLite와 첨부는 영구 볼륨에 둔다. 인스턴스를 여러 개 띄우려면 Postgres와 객체 저장소로 옮겨야 한다.
- **Vercel 서버리스가 맞지 않는 이유**:
  - 파일 시스템이 읽기 전용이라 SQLite와 첨부를 저장할 수 없다.
  - 백그라운드 예약 스레드가 돌지 않는다.
  - Python 런타임에 Node가 없다.
  - 패키지 크기 제한이 있다.

  Vercel을 쓰려면 웹만 올리고 워커·DB·파일은 따로 두는 구성으로 다시 설계해야 한다(6장 2번).
- **비밀값**: `ANTHROPIC_API_KEY`, `SECRET_KEY`, `ADMIN_PASSWORD_HASH`는 환경 변수로 받는다. 이 PC에는 아직 API 키가 없다(검증은 Claude Code CLI로 했다).

### 4.6 비용 추정

| 경우 | 건수 | 추정 비용 | 근거 |
|---|---|---|---|
| 월간 새 공고 | 약 80~90건/월 (1년치 1,010건 기준) | 월 $0.1 미만 | 캐시가 찬 실행 1,010건 $0.74 → 건당 약 $0.0007 |
| 첫 실행(캐시 없음) | 1,010건 | 약 $2.4 | 1회차 실측 |
| 전체 이력 백필 | 약 13,700건(4개 게시판 전체 쪽) | 약 $5~$16 (Batches 50% 반영) | 건당 $0.0007~0.0024 × 건수 ÷ 2 |

CLI가 보고한 비용은 Claude Code가 쓰는 1시간 캐시 쓰기 단가를 포함한다. API에서 5분 캐시를 쓰면 조금 달라진다. 실제 단가는 구현 7단계에서 `llm_calls`로 다시 잰다.

## 5. 검증 결과 (2026-11-24, CLI)

- 방법: `plan/validation/run_cli.sh`. 배포 파이프라인과 같은 시스템 프롬프트·JSON 스키마·모델·effort로 `claude -p`를 저장소 밖 빈 폴더에서 돌렸다(프로젝트 CLAUDE.md·도구·MCP를 끔). 기관별로 50건씩 나눠 6개를 병렬로 처리했다. 입력·출력은 `data/validation/<실행>/`(git 제외)에 있다.
- 비교 기준: `.team/out/classification.jsonl`. 같은 날 Orca 분할 워커 5개(Sonnet 5.5, medium)가 v0 기준(`.team/classify-guide.md`)으로 분류한 결과다.

| 항목 | 1회차 `20261124-v1-low` | 2회차 `20261124-v1-low-repeat` |
|---|---|---|
| 호출 · 공고 | 21 · 1,010 | 21 · 1,010 |
| 빠짐 · sub 불일치 · 실패 | 0 · 0 · 0 | 0 · 0 · 0 |
| 비용 | $2.387 (캐시 없음) | $0.740 (캐시 적중) |
| 호출당 평균 | 10.9~18.3초 | 10.5~16.6초 |
| 확신도 high / mid / low | 906 / 98 / 6 | 906 / 100 / 4 |
| Orca 분류와 분류 일치 | **98.9%** (NIPA 100 · NIA 98.7 · KCA 100 · RAPA 98.5) | **99.1%** |
| Orca 분류와 분류+하위 유형 일치 | 94.8% (RAPA 82.0) | 94.7% |
| 1회차와 2회차 사이 일치(재현성) | 분류 **99.8%**, 분류+하위 유형 97.9% | |

- **분류가 달라진 11건**(1회차, 기준 대비)
  - NIA 8건: 공모사업의 사전규격 공개 5건, 위탁연구 3건(그중 2건은 위탁연구의 사전공개)
  - RAPA 3건: 일경험 인턴, 협약형 제작지원, 자문단 모집
  - 모두 v0 기준에서도 워커 보고서가 '판단이 어려웠다'고 적은 유형이다. 2회차에서 1회차와 달라진 2건(위탁연구 202, 일경험 인턴 855)도 같은 유형이다.
- **RAPA 하위 유형 차이**: 대부분(20건) '채용 합격자 발표'다. v1이 규칙 7에 '합격자 발표 → 기타/결과'를 넣으면서 생긴 의도된 차이다. 나머지는 지원사업 ↔ 참가·교육 8건 등이다.
- **CLI와 API의 차이**: 같은 모델·프롬프트·스키마를 쓰지만, CLI는 구조화 출력을 자체 도구로 감싸고 1시간 캐시를 쓴다. 그래서 구현 뒤 API 경로로 같은 표본을 다시 재야 한다(`02` 7단계).

## 6. 결정 사항 (2026-11-24 Q&A)

설계 문서에 결정 기록으로 남겼다(`docs/설계(안)/docs/40_결정기록.md` ADR-045~052, 미결은 `41_미결사항.md`). 모두 **구현 전**이다.

| 항목 | 결정 | 기록 |
|---|---|---|
| AI 재도입 범위 | 분류 + 표준 필드 추출(규칙으로 못 찾은 칸만 API). ADR-044를 이 범위에서 대체 | ADR-045 |
| 배포 대상 | 컨테이너(Python 3.12 + Node 20) + 영구 볼륨, 웹·워커 두 프로세스. Vercel 서버리스는 쓰지 않음 | ADR-046 |
| 수요자 화면 노출 | 유형 필터와 배지. 처음에는 공모지원사업만 보이고, 입찰공고·기타는 필터로 표시 | ADR-047, F-SVC-29 |
| 경계 규칙 | v2로 확정: 위탁연구 → 입찰공고(협상공모), 공모사업의 사전공개 → 입찰공고(사전규격), 채용 합격자 발표 → 기타(채용) | ADR-048 |

| kordoc | 도입, OCR 끔, CLI 하위 프로세스, 실패 시 extract.py | ADR-050 |
| 미분류 공고 | 수요자 기본 목록에 넣고 '미분류' 배지 | ADR-052 |
| 표준 필드 | 규칙은 모든 유형, API 보완은 공모지원사업만. 공고 내용은 원문 발췌(생성 요약 없음). 상세 화면의 '첨부 구조화' 블록을 표준 5칸으로 바꾸고 '해당 없음'은 흐리게 | ADR-051, F-SVC-30 |
| 월 예산 상한 | **미결**: 실측 전까지 상한 없이 기록만 한다(`llm_calls`, 운영 화면 월 합계) | I-11 |
