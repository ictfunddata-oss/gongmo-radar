# kordoc 도입 검토 — 첨부(HWP·HWPX·PDF) 읽기

- 작성: 2026-11-24 · 결론: **웹앱에 넣을 수 있다. 다만 MCP 서버가 아니라 CLI를 하위 프로세스로 부르는 방식으로, 컨테이너 배포(Python + Node 20)에서만 권장한다.** Vercel 서버리스 같은 Python 전용 실행 환경에서는 쓰기 어렵다.

## 1. kordoc이 무엇인가 (확인한 사실)

| 항목 | 내용 |
|---|---|
| 배포 | npm 패키지 `kordoc` (저장소 github.com/chrisryugj/kordoc), 라이선스 **MIT** |
| 버전 | 이 PC의 MCP 설정은 `kordoc@4.24.59` 고정, npm 최신은 4.25.8 (2026-11-24 확인) |
| 실행 환경 | **Node 20 이상** |
| 진입점 | CLI `kordoc` (파일 → markdown·json·chunks), MCP 서버 `kordoc-mcp` (stdio) |
| 크기 | 패키지 33MB(파일 260개). 선택 의존성 sharp·pdfjs-dist·@hyzyla/pdfium·onnxruntime-node·zxing-wasm 은 따로 늘어난다 |
| OCR | 내장 PP-OCRv5(한국어). `--ocr`를 주면 첫 사용 때 모델(약 18MB)을 내려받는다. 수식 OCR은 별도(약 155MB) |
| 지원 형식 | HWP 3~5, HWPX, HWPML, PDF, XLS(X), DOCX, 이미지. **zip은 지원하지 않는다**(시험에서 HWPX로 오인해 실패) |

## 3. 웹앱에서 쓰는 방법 비교

| 방법 | 구성 | 판단 |
|---|---|---|
| A. CLI 하위 프로세스 (**권장**) | 수집 워커가 `kordoc <파일> --format json`(또는 markdown)을 시간 제한을 두고 부르고, 결과를 `attachments.text_body`에 저장한다 | 결정적이고 단순하다. 웹 요청 경로와 떨어져 있다. Python 쪽은 `subprocess.run` 래퍼 하나면 된다 |
| B. MCP 서버를 앱이 직접 부름 | 앱이 MCP 클라이언트가 되어 stdio로 `parse_document` 호출 | 같은 일을 프로토콜 한 겹 더 거쳐 한다. 이득이 없다 |
| C. Claude API MCP 커넥터 | API 요청에 `mcp_servers`로 원격 MCP를 붙여 모델이 직접 문서를 읽게 함 | 커넥터는 **URL 기반 원격 MCP**만 붙는다. kordoc은 stdio이고 파일 경로를 받는다. 우리 서버의 파일을 읽히려면 kordoc을 HTTP MCP로 따로 띄워야 하고, 모델 호출마다 도구 왕복 비용이 든다. 비권장 |

> MCP는 사람이나 에이전트가 대화 중에 문서를 다룰 때 편한 방식이다. 정해진 순서로 도는 수집 파이프라인에는 CLI(A)가 맞다.

## 4. 배포 조건

1. **실행 환경**: Python 3.12와 Node 20을 함께 담은 컨테이너. 예: `python:3.12-slim`에 Node 20 설치. 버전은 고정하고(`npm i -g kordoc@<버전>` 또는 `npx -y kordoc@<버전>`), 바꿀 때는 비교 시험을 다시 돌린다.
2. **OCR을 켤 경우**: onnxruntime-node와 모델을 이미지 빌드 때 미리 받아 둔다(런타임 다운로드에 기대지 않음). 캐시 폴더는 쓰기가 가능해야 한다. 메모리 1GB 이상을 권장한다(실측 필요).
3. **격리**: 첨부는 외부에서 받은 파일이다. 별도 사용자로 실행하고, 파일당 시간 제한(예: 60초, OCR 120초)과 출력 크기 상한을 두며, 네트워크는 막고, 실패하면 기존 추출기로 넘어간다.
4. **배치 위치**: 웹 요청 중에는 부르지 않는다. 수집 워커(자동화)에서만 부른다.
5. **Vercel 서버리스는 부적합**: Python 런타임에 Node가 없다. 패키지·모델 용량 제한, 읽기 전용 파일 시스템(SQLite·첨부 저장 불가), 백그라운드 예약 실행 불가 문제도 이미 있다(`plan/01` 4.5).

## 5. 적용 순서 제안

1. `app/services/extract.py` 앞에 kordoc 경로를 추가한다. 형식 감지 → zip이면 먼저 풀기 → hwp/hwpx를 pdf보다 먼저 → kordoc 호출 → 실패하면 기존 추출기. 결과에는 어떤 경로로 읽었는지 기록한다(`text_status`에 `ok:kordoc` 등).
2. 표가 HTML(`<table>`)·마크다운 표로 나오므로, 표준 필드 추출(입찰개요 키-값, 지원대상 표)은 이 구조를 이용한다.
3. OCR은 RAPA 이미지 PDF처럼 글자가 0인 파일에만 켜고(`--ocr`는 필요한 쪽만 인식한다), 결과에는 'OCR' 표시를 남겨 화면에서 원문 확인을 안내한다.
4. 비교 시험: 핸드오프 문서(`docs/핸드오프/상세화면_표준필드_20261124.md`) 부록 A의 40건으로 기존 추출기와 kordoc의 필드 채움률을 비교한 뒤 기본값을 바꾼다.

## 6. 남은 불확실성

- OCR 메모리·CPU 사용량과 컨테이너 크기는 실측하지 않았다.
- kordoc은 개인 저장소에서 관리되고 변경이 잦다(4.24 → 4.25). 버전을 고정하고, 갱신은 시험 뒤에 한다.
- PDF 표 감지는 문서마다 결과가 다르다(`--no-tables` 옵션도 비교 대상).
