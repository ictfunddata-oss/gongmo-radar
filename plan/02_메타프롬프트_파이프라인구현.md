# 메타프롬프트 — 웹앱 배포용 수집·분류·자동화 파이프라인 구현 지침

> [!warning] 대체됨(2026-11-24)
> 2차 Q&A 결정을 반영해 구현 지시를 `plan/00_구현핸드오프.md` 한 문서로 합쳤다. **구현에는 00을 쓴다.** 첫 메시지는 00 부록 A, API 호출 형태는 00 부록 B.3이다. 아래는 이전 지시문으로, 범위(표준 필드 제외, 버그 2건, API 키 전제)가 00과 다르다.

## 역할

당신은 이 저장소(공모사업 수집 웹앱, Python 3.12 · Flask · SQLite)에 **수집 → 첨부 글자 → API 분류 → 자동 실행** 파이프라인을 붙이는 구현 담당이다. 저장소의 `AGENTS.md` 행동 지침을 따른다. 요약하면 다음과 같다.
- 추측하지 말고 묻는다.
- 최소한의 코드만 쓴다.
- 바뀐 모든 줄이 이 지시로 거슬러 올라가야 한다.
- 검증될 때까지 반복한다.

## 먼저 읽을 것 (이 순서로)

1. `CLAUDE.md`, `AGENTS.md`: 명령, 구조, 데이터 규칙
2. `plan/01_핸드오프_배포파이프라인.md`: 목표 구성, 결정 사항, 검증 결과
3. `plan/03_kordoc_도입검토.md`: 첨부 읽기 방식
4. `plan/prompts/`의 분류 런타임 프롬프트: `classify_v2`(ADR-048)가 작성·검증되어 있으면 그것을, 아니면 `classify_v1`을 쓴다. 수정하지 않는다
5. `app/crawler/runner.py`, `app/automation/pipeline.py`, `app/automation/scheduler.py`, `app/services/attach_text.py`, `app/services/extract.py`, `app/schema.sql`, `app/db.py`
6. `plan/validation/`의 `make_input.py`·`evaluate.py`: 분류 입력을 어떻게 만들고 결과를 어떻게 검사하는지

## 목표

배포된 웹앱의 자동화가 다음을 한 번에 돈다. 각 단계는 따로 켜고 끌 수 있다.

1. **수집**: 기존 `crawler.crawl()`을 그대로 쓴다.
2. **첨부 글자**: kordoc CLI를 하위 프로세스로 부르고, 실패하면 기존 `extract.py`로 넘어간다. zip은 먼저 풀고, hwp/hwpx를 pdf보다 먼저 읽는다.
3. **분류**: 아직 라벨이 없거나 제목·본문이 바뀐 공고를 Claude API로 분류한다(입찰공고 / 공모지원사업 / 기타 + 하위 유형).
4. **기록**: 실행마다 단계별 건수와 API 토큰·비용·요청 ID를 남긴다.

표준 필드 추출 단계(ADR-045)는 `extract_v1` 프롬프트가 검증된 뒤 별도 지시로 진행한다. 이번 지시의 범위가 아니다.

## 지켜야 할 설계 (바꾸려면 먼저 사용자에게 묻는다)

### API 호출
- SDK는 공식 `anthropic` Python SDK만 쓴다(1.x, `requirements.txt`에 버전 고정). 원시 HTTP나 다른 공급자 호환 계층은 쓰지 않는다. 자격증명은 `ANTHROPIC_API_KEY` 환경 변수로 받는다.
- 모델 ID는 `claude-sonnet-5-5`다. 설정(`CLASSIFY_MODEL`)으로 둔다. 날짜 접미사를 붙이지 않는다.
- 요청 형태는 문서로 확인한 것만 쓴다.

```python
client.beta.messages.create(
    model=cfg["CLASSIFY_MODEL"],
    max_tokens=8000,                                   # 50건 묶음 기준. 잘리면(stop_reason == "max_tokens") 묶음을 반으로 나눠 다시 보낸다
    betas=["server-side-fallback-2026-07-01"],
    fallbacks="default",                               # 거절(refusal) 시 서버가 대체 모델로 다시 실행. Batches 요청에서는 빼야 한다
    system=[{"type": "text", "text": SYSTEM_PROMPT, "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": "다음 items를 분류하세요.\n<items>\n" + items_json + "\n</items>"}],
    output_config={"effort": "low", "format": {"type": "json_schema", "schema": SCHEMA}},
)
```

- `temperature`·`top_p`·`top_k`는 보내지 않는다(이 모델에서 400). assistant prefill도 쓰지 않는다. `thinking`은 생략한다(적응형 기본).
- 동기 호출은 위처럼 서버 측 대체(`fallbacks="default"`)를 켠다. 끄려면 사용자에게 묻는다. 응답의 `stop_reason`부터 확인하고, 대체 모델까지 `refusal`이면 그 묶음을 '분류 보류'로 기록하고 다음으로 넘어간다. 대체가 일어나면 `content`에 `fallback` 블록이 섞이므로, JSON은 `type == "text"`인 블록에서 읽는다(`content[0]`을 가정하지 않는다). `response.usage.iterations`에 `fallback_message`가 있으면 `llm_calls`에 대체 여부와 실제 모델(`response.model`)을 기록한다.
- 대량 재분류(백필)는 Message Batches API를 쓴다(`client.messages.batches.create`, 50% 할인, 24시간 이내, `fallbacks` 불가). 결과는 `custom_id`로 맞추고 순서를 믿지 않는다.
- 오류는 구체적인 예외부터 잡는다: `RateLimitError` → `APIStatusError`(5xx는 재시도) → `APIConnectionError`. SDK 기본 재시도(2회)를 쓰고 직접 재시도 루프는 만들지 않는다.

### 입력과 출력
- 입력 항목은 `plan/validation/make_input.py`와 같다: ann_id·board·post_no·title·biz·site_status·period·posted·본문 앞 300자(`mask_contacts` 적용)·첨부 이름 6개. **작성자(writer)는 보내지 않는다.** 이 조립 코드는 앱 안에 한 번만 두고, 검증 스크립트도 그것을 쓰게 바꿔도 된다.
- 출력은 스키마로 강제된다. 그래도 앱에서 다시 검사한다: 입력의 모든 ann_id가 한 번씩 있는지, sub가 class에 속하는지(`plan/validation/evaluate.py`의 SUB 표). 어긋난 항목만 한 번 다시 보내고, 그래도 어긋나면 '수동 확인'으로 둔다.

### 저장
- 새 표 `announcement_labels`: ann_id, class, sub, confidence, reason, source('api'|'manual'), prompt_version('classify_v1'), model, request_id, input_hash, labeled_at.
- `schema.sql`에 추가하고, 기존 DB 이행이 필요하면 `db._migrate()` 방식을 따른다. 기존 표의 열은 바꾸지 않는다(원천 보존).
- **사람이 고친 라벨(source='manual')은 API가 덮어쓰지 않는다.**
- 다시 분류할 대상: 라벨 없음, 또는 input_hash(분류 입력의 해시)가 바뀜, 또는 prompt_version이 현재와 다름. 같은 입력을 두 번 보내지 않는다.
- API 호출 기록 표 `llm_calls`: 실행 ID, 단계, 모델, 요청 ID(`response._request_id`), 입력·출력·캐시 토큰, 추정 비용, 결과(ok/refusal/error), 시각.

### 자동화
- `automation/settings.py`의 DEFAULTS에 단계 스위치(`attach_text`, `classify`)와 실행당 상한(`classify_max_items`, 기본 200)을 추가한다. 기본값은 꺼짐이다.
- `pipeline.run_pipeline()`에 단계를 순서대로 붙인다. 한 단계가 실패해도 다음 단계는 돈다(기존 원칙).
- 박동(heartbeat)은 긴 단계 안에서도 갱신되게 한다. 지금은 게시판 하나가 끝날 때만 갱신되어, 3분(LOCK_TTL)을 넘는 단계에서 다른 프로세스가 잠금을 가져갈 수 있다(`pipeline.py`의 `beat` 호출 위치).
- 수집기가 첨부를 받는 동안 DB 쓰기 트랜잭션을 열어 두지 않게 한다. `runner.py`에서 `download_missing()`을 부르기 전에 commit한다. 지금은 웹 쪽 쓰기가 `database is locked`로 실패한다(재현 확인됨).

### 관리 명령·화면
- CLI 명령 `classify`: `[--board 코드] [--limit N] [--batch] [--dry-run] [--redo]`. `--dry-run`은 보낼 묶음 수·건수·추정 토큰만 출력하고 API를 부르지 않는다.
- 운영 화면은 최소한만 만든다. 라벨 분포, '수동 확인'·'분류 보류' 목록, 최근 실행의 토큰·비용.
- 수요자 화면에는 ADR-047대로 유형 필터(처음에는 공모지원사업만)와 배지를 단다(F-SVC-29, 규칙은 `docs/설계(안)/docs/13_기능정의서_서비스.md` §4.13). 분류 전 공고를 기본 표시에 넣을지는 구현 전에 사용자에게 묻는다.

### kordoc
- `app/services/kordoc.py`에 하위 프로세스 래퍼 하나를 둔다. 실행 파일 경로와 버전은 설정으로 받는다(`KORDOC_CMD`, 예: `npx -y kordoc@4.24.59`). 시간 제한(기본 60초, OCR 120초)과 출력 상한을 둔다. 0이 아닌 종료 코드, 시간 초과, 빈 출력은 실패로 보고 기존 추출기로 넘어간다.
- OCR(`--ocr`)은 기존 추출 결과가 empty인 PDF에만 쓴다. 설정 `KORDOC_OCR`, 기본 꺼짐.

## 하지 않을 것

- 수요자 화면·검색·방문 집계 등 이 지시와 관계없는 코드는 고치지 않는다. 눈에 띄는 문제는 보고서에 적기만 한다.
- 분류 런타임 프롬프트와 스키마(`plan/prompts/`)를 고치지 않는다. 고칠 필요가 보이면 다음 버전 초안을 따로 만들고 보고한다.
- 테스트에서 실제 API·네트워크·kordoc을 부르지 않는다. 클라이언트와 하위 프로세스는 가짜로 바꿔 끼운다.
- 비밀값을 코드·로그·커밋에 넣지 않는다.

## 작업 순서와 검증

1. 버그 두 개를 고친다(첨부 받는 중 트랜잭션, 박동). → 검증: 쓰기 잠금을 재현하는 테스트와 박동 갱신 테스트가 통과한다.
2. `announcement_labels`·`llm_calls` 스키마와 이행 → 검증: 빈 DB와 기존 DB(이행) 모두에서 `init-db` 성공, 기존 107개 테스트 통과
3. 분류 서비스(입력 조립 → 묶음 → 호출 → 검사 → 저장) → 검증: 가짜 클라이언트로 정상·빠짐·sub 불일치·refusal·max_tokens 경우 테스트
4. `classify` CLI(`--dry-run` 포함) → 검증: dry-run 출력, 실제 실행은 사용자가 API 키를 넣은 뒤 `--limit 20`으로 한 번
5. kordoc 래퍼와 첨부 글자 단계 → 검증: 가짜 하위 프로세스로 성공·실패·시간 초과 → 폴백 테스트
6. 자동화 단계 연결, 운영 화면, 수요자 유형 필터 → 검증: 자동화 테스트(`tests/test_automation.py`) 확장, 화면 직접 확인
7. 품질 확인 → `plan/validation/run_cli.sh` 결과(기준 분류 일치율)와 같은 표본으로 API 경로 결과를 비교한다. 분류 일치율이 CLI 검증 값보다 크게 낮으면(5%p 이상) 원인을 보고한다.

완료 보고 전에 `python -m unittest discover -s tests -q`를 돌린다(이 저장소에는 pnpm·tsc가 없다). 화면을 바꿨으면 `./run-app.sh`로 띄워 확인한다. 실패는 실패라고 적는다.
