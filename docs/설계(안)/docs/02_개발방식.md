# 개발 방식

## 1. 개발 원칙

- 내부 자체 개발로 진행하고, 이미 가동 중인 NIPA 수집기(`nipa/nipa_crawler.py`)를 공통 구조로 확장한다.
- PoC는 NIPA 2026년 공고 121건으로 작게 시작하고, 정확도를 잰 뒤 대상을 넓힌다.
- 수집·선별·분류를 각각 따로 실행할 수 있게 나눈다. 한 단계를 고쳐도 다른 단계는 다시 돌리지 않는다(D-01 §1).

## 2. 기술 스택

| 구 분 | 현재(PoC) | 확장 시 | 비고 |
|---|---|---|---|
| 언어 | Python 3 | 동일 | 기존 수집기와 같은 언어 |
| HTTP·파싱 | requests, BeautifulSoup(lxml) | 동일 | 정적 HTML 게시판 |
| 동적 페이지 | 없음 | Ajax 직접 호출 우선, 필요 시 Playwright | KOTRA 등(F-CRW-09) |
| 저장소 | SQLite(`nipa/data/nipa.db`) | 운영 DB 이관 검토 | 이관 대상·시기는 I-06과 함께 결정 |
| AI | 없음 | Claude API(Python `anthropic` SDK) | 이 PC에 SDK 1.5.0과 API 키 준비됨 |
| 내보내기 | openpyxl(엑셀), HTML 대시보드 | 동일 + PIMS 연계 | |
| 실행 | `update_nipa_dashboard.bat` 수동 | 스케줄러(보류, ADR-005) | |

## 3. 모듈 구조(안)

현재는 `nipa/` 폴더에 NIPA 전용 코드만 있다. 기관을 늘리기 전에 아래 구조로 정리한다.

```
pipeline/
├── crawl/
│   ├── core.py          # 세션·재시도·요청 간격·robots.txt 확인·실행 기록
│   ├── adapters/        # 기관 어댑터 — 기관 하나 = 파일 하나
│   │   ├── nipa.py
│   │   ├── nia.py
│   │   └── ...
│   └── run.py           # 어댑터 목록을 돌며 증분 수집
├── ai/
│   ├── client.py        # AI 호출 단일 진입점(모델·공급자 교체 지점)
│   ├── select.py        # 선별(FS-SEL)
│   ├── classify.py      # 분류·추출(FS-CLS)
│   ├── prompts/         # 프롬프트 원문 — 파일명에 버전(select_v1.md)
│   └── schemas/         # 출력 JSON 스키마 — 분류 체계 버전과 짝
├── store/
│   ├── schema.sql       # D-20 데이터 설계
│   └── migrate.py
├── service/
│   ├── build_dashboard.py
│   └── export.py
└── tests/
    ├── fixtures/        # 기관별 목록·상세 HTML 스냅샷
    └── test_adapters.py
```

## 4. 기관 어댑터 방식

어댑터는 게시판마다 다른 부분만 담고, 요청 간격·재시도·저장은 `core.py`가 공통으로 처리한다.

| 어댑터가 정하는 것 | 내용 |
|---|---|
| 기관·게시판 정보 | 기관명, 게시판명, 목록 URL, 수집 방식(정적·Ajax·브라우저) |
| 목록 파싱 | 게시물 ID, 목록 번호, 제목, 게시일, 마지막 페이지 판정 |
| 상세 파싱 | 사업구분, 신청기간, 작성일, 조회수, 본문, 첨부 목록 |
| 기관별 예외 | 날짜 형식, 상시모집 표기, 공지 고정글 처리 |

> [!tip] NIPA 수집기에서 얻은 교훈
> 마지막 묶음 페이지(31~36쪽)에서는 '마지막 페이지' 링크가 사라져 첫 전체 수집이 31쪽에서 끝났다. 페이지 링크 번호의 최댓값으로 판정하도록 고친 뒤 353건을 모두 받았다. 기관마다 이런 예외가 있으므로 어댑터별로 HTML 스냅샷 테스트를 둔다(§7).

## 5. AI 호출 방식

> [!note] 공급자
> AX계획은 "내부 PoC 및 검증을 통해 외부LLM(OpenAI, 법제처 등) API 연동"으로 되어 있다. 이 설계는 이미 환경이 갖춰진 Claude API로 PoC를 진행하되, 호출부를 `ai/client.py` 하나로 모아 공급자를 바꿀 수 있게 한다(P7). 최종 공급자와 비용 승인은 I-08.

| 항목 | 방식 | 이유 |
|---|---|---|
| 모델 | `claude-sonnet-5-5`(Claude Sonnet 5.5), effort `medium` | '26.10.6 사용자 결정(ADR-009). `.env`의 `AI_MODEL`·`AI_EFFORT`로 바꿀 수 있음. 거절 대비 서버측 fallback(`fallbacks="default"`) 사용 |
| 출력 형식 | 구조화 출력(JSON 스키마 강제) | 분류값이 정해진 목록 밖으로 나가지 않게 하고, 파싱 실패를 없앰 |
| 프롬프트 구성 | 고정부(역할·분류 기준·내역사업 목록) + 가변부(공고 1건) | 고정부를 앞에 두어 프롬프트 캐시를 적용 |
| 대량 처리 | 메시지 배치(Message Batches) | 최초 일괄 분류·재분류처럼 급하지 않은 작업은 배치로 보내 비용 절반 |
| 일상 처리 | 신규 공고만 건별 호출 | 하루 신규 공고가 적어(NIPA 2026년 월평균 약 13건) 건별 호출로 충분 |
| 안전장치 | 응답 거절(refusal) 확인 후 결과 저장, 실패 건은 '검토 필요'로 | 판정이 비어 있는 채로 노출되지 않게 |
| 기록 | 모델명·프롬프트 버전·분류 체계 버전·입출력 토큰 수 저장 | 재현성(P2)과 비용 추적 |

**비용 추정**(PoC 121건, [추정] — PoC에서 실측해 갱신. 단가가 옛 값이라 배포용 추정은 §8을 본다)

| 항목 | 가정 | 추정 |
|---|---|---|
| 건당 가변 입력 | 공고 메타 + 본문(2026년 평균 717자) ≈ 1천 토큰 | 121건 × 1천 = 약 12만 토큰 |
| 고정부(캐시 읽기) | 분류 기준 + 내역사업 목록 ≈ 4천 토큰 | 121건 × 4천 = 약 48만 토큰 |
| 출력(사고 과정 포함) | 건당 약 1.5천 토큰 | 약 18만 토큰 |
| 합계 | 입력 $4/백만, 캐시 읽기 $0.20/백만, 출력 $20/백만 토큰 | 약 4~5달러(배치 시 절반) |

## 8. 배포 시 정기 실행 구조와 비용 추정 (2026-10-19, ADR-038)

### 8.1 정기 실행 구조

```
[예약] 관리자 화면에서 정한 요일·시각
   │  (서버 안 예약 실행기 15초마다 점검 / 별도 데몬 / cron·작업 스케줄러 → automation-run)
   ▼
[잠금] DB 잠금 획득 — 이미 실행 중이면 건너뜀
   ▼
① 수집 ──▶ ② 제목 규칙 선별 ──▶ ③ AI 판별 ──▶ ④ 노출 재계산
 (무료)       (무료)             (Claude API,     (무료)
 게시판별      선정결과·설명회     1회·월 상한)      마감일·상시모집·컨설팅뿐
 증분 수집     등은 AI 없이 제외                    규칙 + 수동 변경 우선
   ▼
[기록] 실행 기록(상태·단계별 건수·상세) → 관리자 화면에서 확인
```

| 배치 방식 | 설명 | 적합한 경우 |
|---|---|---|
| ① 서버 안 예약 실행기(기본) | 웹 서버 프로세스가 예약을 함께 처리. 별도 구성 없음 | 서버 한 대, 상시 켜 둠 |
| ② 웹과 데몬 분리 | 웹은 `AUTOMATION_SCHEDULER=0`, 별도 서비스로 `automation-daemon` | 웹을 여러 개 띄우거나 웹 재시작과 분리하고 싶을 때 |
| ③ 작업 스케줄러 | cron·Windows 작업 스케줄러가 `automation-run`을 호출 | 서버리스·관리형 환경, 기관 표준 스케줄러 사용 |

- 권장 시작 일정: 평일 하루 1~2회(예: 06:00, 14:00). 게시판 요청 간격(`CRAWL_DELAY`)과 robots.txt 준수는 그대로.
- 안전장치: 기본값 꺼짐, AI 1회·월 건수 상한, 키 없음·연속 실패 시 AI 단계만 중단, 판별 대상 게시일 기준.
- API 키는 서버 환경변수(`ANTHROPIC_API_KEY`)로만 두고 코드·저장소·화면에 쓰지 않는다.
- 서버리스(예: Vercel) 환경은 오래 걸리는 수집·판별과 상시 실행기가 맞지 않으므로 ③ 방식 또는 상시 서버를 쓴다(I-06 DB 이관과 함께 결정).

### 8.2 AI 비용 추정 [추정 — 운영하며 실측해 갱신]

| 항목 | 값 | 근거 |
|---|---|---|

| 월 신규 공고 | NIA 약 70건(대부분 입찰), NIPA 약 8건, RAPA 약 11건 | 2026-03~09 평균 |

| 시나리오 | 월 AI 대상 | 월 비용(USD) | 원화(1,400원 가정) |
|---|---|---|---|
| A. 지금 구조 그대로(NIA 입찰도 AI 판별) | 약 90건 | 약 $1.1 | 약 1,600원 |
| B. NIA 입찰 게시판은 규칙으로 제외(AI는 [공모]만) | 약 25건 | 약 $0.2 | 약 300원 |
| C. 기관 10곳으로 확대(A 기준, 기관당 NIPA형 20건/월 추가) | 약 230건 | 약 $2.1 | 약 3,000원 |
| D. 과거 공고 1,000건 일괄 판별(1회성, 배치 시 절반) | 1,000건 | 약 $9(배치 $4.5) | 약 12,600원 |

- 토큰 추정이 3배 틀려도 시나리오 A는 월 $4 안팎. 월 상한(기본 300건)을 두면 최악도 약 $4.3.
- 모델을 Haiku 5.5($0.10/$0.50)로 바꾸면 약 1/20이지만 정확도는 검증 전(E-001 재실험 필요).
- 제외 항목: 서버·도메인·인증서·DB 호스팅 비용, 인건비.
- 반영됨(ADR-039): NIA 입찰 게시판은 제목 말머리 규칙으로 AI 호출 전에 처리하므로 현재 구조는 시나리오 B(월 약 $0.2)에 해당한다. 규칙은 운영 화면 '선별 규칙'에서 관리한다.

## 9. 배포 파이프라인 (2026-11-24, ADR-045~052)

> 구현은 저장소의 `plan/00_구현핸드오프.md` 한 문서로 맡긴다(결정·계약·단계·관문·명세). 배경과 검증 결과는 `plan/01_핸드오프_배포파이프라인.md`, kordoc 판단은 `plan/03_kordoc_도입검토.md`에 있다. 아래는 결정 사항 요약이며 아직 구현하지 않았다.

### 9.1 구성

```
 워커 프로세스 (automation-daemon, 예약 실행)
   ├─ ① 수집        crawler.crawl() — 기존 그대로
   ├─ ② 첨부 글자    zip 풀기 → kordoc CLI(hwp·hwpx 우선) → 실패 시 extract.py   (ADR-050)
   ├─ ③ 분류        Claude API · classify_v2 · 구조화 출력                     (ADR-045·048)
   ├─ ④ 표준 필드    규칙 → 못 찾은 칸만 Claude API · extract_v1               (ADR-045)
   └─ 기록          automation_runs + llm_calls(토큰·비용·요청 ID·대체 여부)
 웹 프로세스 (gunicorn, AUTOMATION_SCHEDULER=0)
   └─ 수요자 화면: 유형 필터, 기본 공모지원사업                                (ADR-047)
 배포: 컨테이너(Python 3.12 + Node 20) + 영구 볼륨(SQLite·첨부)               (ADR-046)
```

### 9.2 정한 값

| 항목 | 값 | 근거 |
